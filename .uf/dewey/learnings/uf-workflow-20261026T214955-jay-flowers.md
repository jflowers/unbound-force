Instruction text that gates delegation prompt contents on a shorthand phrase must define the phrase at the decision point it controls, and resume claims over a paused-exit variant list must be split by where each variant actually fires. Verified on update-run-pipeline-plan PR 839 review (2026-10-26, feedback item 4): the command, spec delta, design D4, and byte-identical scaffold mirror all carried "delegate /uf.unleash again with the same command_path and no routing context — the child resumes from its durable state" unconditionally across all eleven paused-exit variants. Two defects compound: (1) "no routing context" is undefined in the user-facing command and is misreadable as "omit the work-item description," which sends the re-run child into uf_unleash_route_decision's fallback human question ("What do you want to build?") that cannot surface from a parented child session — the delegation hangs until timeout; (2) tier-routing-dirty-tree and tier-routing-missing-tooling exit before any feature branch or durable checkpoint exists (tier-routing checkpoints only on success), so "resumes from durable state" is false for them — the re-run is a fresh restart needing description + issue refs re-supplied, with the orchestrator selecting the path from its [BLOCKED: <variant>] annotation. A spec scenario that exercises only one variant class (implement-phase-checkpoint) hid the over-broad claim from spec review. Authoring-side recipe (complement to the reviewer-check in uf-workflow-20261026T182020-jay-flowers): when command/spec/design text references a tool's exit variants, (a) define every shorthand inline where it gates behavior, (b) state resume/restart semantics per variant class, verified against where each variant fires in the tool source, and (c) include at least one spec scenario per class so an unconditional claim cannot survive review; sync the correction across command, mirror, spec delta, design, and the filed docs-gate issue body in the same commit (compiled/documentation-pipeline).
